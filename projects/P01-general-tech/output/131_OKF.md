# Open Knowledge Format (OKF) 分析報告

> 調研日期：2026-07-23 | 資料來源：Google Cloud Blog, SPEC.md v0.1, knowledge-catalog repo, awesome-okf, OKFy, okfcli

---

## 1. 這個技術解決什麼問題？

**OKF 解決的問題是：AI agent 所需的「知識」（knowledge）缺乏一個跨系統、跨供應商、跨工具的標準化表示格式，導致知識碎片化、無法互通、難以版本管理。**

具體來說，當前的現狀是：

- 每個 AI agent 框架（LangChain, ADK, Claude Code, Cursor 等）各自定義自己的知識注入方式（prompt template, RAG pipeline, tool description, AGENTS.md/CLAUDE.md 等）
- 同一份知識（例如 BigQuery 資料表 schema）在不同 agent 間需要重複撰寫、重複轉換
- 知識與程式碼分離，無法享受 git diff、PR review、blame 等軟體工程基礎設施
- 知識的「生產者」（資料工程師、領域專家）與「消費者」（AI agent）之間缺乏共同介面

OKF 不解決的問題（spec 明確列為 non-goal）：
- 不定義固定的概念分類法（taxonomy）
- 不規定儲存、服務或查詢基礎設施
- 不取代領域特定 schema（Avro, Protobuf, OpenAPI 等）— OKF 引用它們，不取代它們

---

## 2. 這個問題為什麼會發生？（背景）

### 2.1 AI agent 的知識需求從「隱式」轉為「顯式」

早期 LLM 應用依賴模型訓練時學到的知識（parametric knowledge）。但 agent 需要操作具體的企業資料庫、API、業務流程，這些資訊不在訓練資料中，必須以某種形式「餵」給 agent。

### 2.2 既有做法各自為政

| 做法 | 代表 | 問題 |
|------|------|------|
| 直接貼文件進 context | 手動 copy-paste | 不可重複、不可版本管理、context window 有限 |
| RAG pipeline | LangChain, LlamaIndex | 需要 embedding 服務、檢索邏輯不透明、結果不可 inspect |
| Agent 專屬設定檔 | AGENTS.md, CLAUDE.md, cursorrules | 單一檔案、無結構化、跨 agent 不互通 |
| 個人知識管理工具 | Obsidian, Notion | 非 agent 原生、無標準 frontmatter 規範、export 格式各異 |
| Metadata as Code | dbt docs, DataHub, OpenMetadata | 綁定特定平台或 schema registry，非 agent 直接可讀 |

### 2.3 Karpathy 的「LLM Wiki」概念（文章明確引用）

Andrej Karpathy 在 2025 年提出的「LLM Wiki」gist 是 OKF 的直接思想來源。核心觀察：
- LLM 擅長處理多檔案的相互引用更新（「一次處理 15 個檔案」）
- 與其讓 agent 每次都重新檢索，不如提供一個共享的 Markdown 庫，隨時間打磨
- 開發團隊負責策展內容，agent 負責讀取和更新

### 2.4 格式標準化的空白地帶

在 OKF 出現前，存在多種「接近但未標準化」的模式：
- Obsidian vault（Markdown + wikilink，但 frontmatter 無強制規範）
- 靜態網站生成器（Hugo, Jekyll, MkDocs — 用 frontmatter 但目的為渲染而非 agent 消費）
- 資料目錄工具（DataHub, Amundsen — 有 schema 但非檔案格式）

這些模式各自解決了部分問題，但缺乏一個「最小公約數」讓不同系統間可以直接交換知識。

## 3. 這個技術是如何解決該問題的？

### 3.1 核心定義

OKF 將「知識」定義為：**一個目錄樹的 Markdown 檔案，每個檔案帶 YAML frontmatter，遵循一小套結構約定。**

```
path/to/bundle/
├── index.md                      # 目錄清單（選擇性，支援漸進式揭露）
├── log.md                        # 更新歷史（選擇性）
├── <concept>.md                  # 根層級的概念文件
└── <subdirectory>/               # 子目錄分組
    ├── index.md
    ├── <concept>.md
    └── <subdirectory>/
        └── …
```

### 3.2 三個強制要求（Conformance）

一個 bundle 符合 OKF v0.1 的條件只有三條：

1. 每個非保留的 `.md` 檔案必須包含可解析的 YAML frontmatter
2. 每個 frontmatter 必須有非空的 `type` 欄位
3. 保留檔名（`index.md`, `log.md`）必須遵循對應章節的結構

**消費端必須寬容處理**：未知 type、缺少選擇性欄位、斷裂的 cross-link、缺少 index.md — 這些都不應導致拒絕。

### 3.3 Frontmatter 結構

```yaml
---
type: <Type name>                  # 必要
title: <Optional display name>
description: <Optional one-line summary>
resource: <Optional canonical URI>
tags: [<tag>, <tag>, …]            # 選擇性
timestamp: <ISO 8601 datetime>     # 選擇性
# … 其他 producer 自訂 key/value
---
```

`type` 是唯一必要欄位，且不註冊中央詞典。Producer 自行選擇描述性名稱，consumer 必須優雅處理未知 type。

### 3.4 Cross-linking（跨文件連結）

使用標準 Markdown 連結表達概念間的關係：

```markdown
# 絕對路徑（建議）
See the [customers table](/tables/customers.md) for the join key.

# 相對路徑
See the [neighboring concept](./other.md).
```

連結的語意由前後文決定（parent/child, references, joins-with, depends-on 等），連結本身不帶類型標記。Consumer 將所有連結視為有向邊。

**Consumer 必須容忍斷裂連結** — 目標不存在的連結不被視為格式錯誤，可能只是「尚未撰寫的知識」。

### 3.5 漸進式揭露（Progressive Disclosure）

`index.md` 檔案讓 agent 或人類可以逐層瀏覽，而不需一次載入整個 bundle：

```markdown
# Section / Group Heading

* [Title 1](relative-url-1) - short description
* [Title 2](relative-url-2) - short description
```

### 3.6 保留檔名

| 檔名 | 用途 |
|------|------|
| `index.md` | 目錄清單（§6） |
| `log.md` | 更新歷史（§7） |

### 3.7 引用（Citations）

概念文件可在 body 底部列出外部來源：

```markdown
# Citations

[1] [BigQuery public dataset announcement](https://cloud.google.com/...)
[2] [Internal data quality runbook](https://wiki.acme.internal/...)
```

### 3.8 版本管理

OKF 使用 `<major>.<minor>` 版本號：
- **minor** 升級：向後相容的新增（新選擇性欄位、新慣用章節標題）
- **major** 升級：可能破壞相容性（重新命名必要欄位、改變保留檔名）

Bundle 可在根目錄 `index.md` 的 frontmatter 中宣告 `okf_version: "0.1"`。

### 3.9 官方參考實作

Google Cloud 在 `GoogleCloudPlatform/knowledge-catalog` 中提供：
- **reference_agent**：Python 實作，從 BigQuery 讀取 metadata + 從網路爬取文件 → 產出 OKF bundle
- **visualizer**：將 bundle 渲染為自包含的互動式 HTML 圖形（Cytoscape.js + marked）
- **範例 bundle**：GA4 e-commerce, Stack Overflow, Bitcoin crypto

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式？

### DA 表：替代方案對照

| 技術名 | 技術解法 | 技術使用前提 | 技術使用副作用 | 技術使用預期效果 |
|--------|----------|-------------|---------------|-----------------|
| **AGENTS.md / CLAUDE.md / cursorrules** | 單一 Markdown 檔案放在專案根目錄，定義 agent 行為規則與專案知識 | 使用支援該約定的 coding agent（Claude Code, Cursor, Copilot 等） | 單一檔案無結構化，無法表達概念間關係；無版本管理（雖在 git 中但無 diff-friendly 結構）；跨 agent 不互通 | Agent 啟動時自動載入，快速建立 context |
| **RAG (Retrieval-Augmented Generation)** | 將文件向量化存入向量資料庫，查詢時檢索相關片段後注入 LLM context | 需要 embedding model、向量資料庫、檢索 pipeline；需要持續維護索引 | 檢索結果不透明（black box）；無法 inspect 檢索邏輯；需要額外基礎設施（vector DB, embedding service）；有 token 成本 | 可處理大量文件，超越 context window 限制 |
| **llms.txt / llms-full.txt** | 網站根目錄放置 `llms.txt` 檔案，列出 AI 相關資源連結與簡短摘要 | 網站維護者主動提供；LLM 或 agent 需支援讀取該檔案 | 通常為單一檔案或連結列表，無結構化內容；無 cross-linking 機制；無版本管理規範 | 提供 LLM 一個輕量的網站入口點 |
| **Obsidian / 個人知識管理 (PKM)** | 使用 Markdown + wikilink 建立個人知識庫，搭配 graph view 視覺化 | 使用者自行維護 vault；需安裝 Obsidian 客戶端 | 非 agent 原生設計；frontmatter 無強制規範；export 格式各異；無標準化 bundle 概念 | 個人知識管理與 graph 視覺化 |
| **Data Catalog (DataHub, OpenMetadata, Amundsen)** | 集中式 metadata 儲存與服務，提供 API 查詢資料資產 | 需要部署與維護 catalog 服務；資料需註冊入 catalog | 綁定特定平台或 schema registry；非 agent 直接可讀（需 API call）；有 vendor lock-in 風險 | 企業級 metadata 管理與 lineage 追蹤 |
| **dbt docs / Docs as Code** | 在程式碼倉庫中維護文件，與程式碼一起版本管理、CI/CD | 使用 dbt 或其他支援 docs-as-code 的工具 | 綁定特定工具生態；文件格式通常為工具特定（dbt 用 YAML + Markdown） | 文件與程式碼同步，可 diff、可 review |

### 切入點差異分析

OKF 與上述方案的核心差異在於：

1. **格式先於服務**：OKF 定義的是檔案格式而非 API 或服務。這意味著不需要部署任何 server、不需要註冊任何 registry、不需要依賴任何供應商。

2. **最小約定**：只有 3 條強制規則（有 frontmatter、有 type、保留檔名守規矩），其餘全部是建議。這讓既有工具（Obsidian, MkDocs, Hugo）可以無痛產出或消費 OKF。

3. **agent 原生**：設計目標明確是「agent 可讀、agent 可寫」。Frontmatter 的 `type` 欄位讓 agent 可以過濾和路由；`index.md` 讓 agent 可以漸進式探索；cross-linking 讓 agent 可以 traverse 知識圖。

4. **git 原生**：Bundle 就是目錄，天然適合 git。知識變更可以走 PR review、diff、blame、CI 驗證。

5. **不綁 LLM 供應商**：OKF 本身不依賴任何 LLM API。Google 的 reference agent 用 Gemini，但社群工具（OKFy, okfcli）完全不需要 LLM。

### 反證表：OKF 的潛在限制

| 限制 | 說明 |
|------|------|
| **無內建查詢引擎** | OKF 是檔案格式，不是資料庫。查詢需要外部工具（grep, okfcli search, MCP server） |
| **無內建新鮮度保證** | 檔案可能過期。社群工具 surface 嘗試解決此問題（code change → build fail） |
| **大規模效能未驗證** | SPEC 提到「可驗證數百萬概念」，但實際大規模場景尚未有公開案例 |
| **v0.1 仍為草案** | 規格可能變動；major 版本可能破壞相容性 |
| **無中央 type registry** | 雖然是設計意圖（去中心化），但可能導致 type 命名碎片化 |
| **非結構化資料處理有限** | 圖片、PDF 等非 Markdown 格式需外部引用或擴展提案（awesome-okf 已有 code/PDF support 提案） |

## 5. User Q&A

### Q1：OKF 是標準，還是 AICodeAgent 能直接用的 skill 或 MCP？還是其他？

**A**：OKF 是**開放規格（open specification）**，不是 skill 也不是 MCP。但它生態中有工具同時提供了 skill 和 MCP。

| 層級 | 是什麼 | 範例 |
|------|--------|------|
| **規格（Specification）** | 定義檔案格式與 conformance 規則的標準文件 | `SPEC.md` v0.1/v0.2，由 Google Cloud 發布，Apache-2.0 |
| **檔案格式（File Format）** | YAML frontmatter + Markdown body 的目錄結構 | 任何符合 SPEC 的 bundle |
| **生態工具（Ecosystem Tools）** | 實作該格式的 producer/consumer 工具 | OKFy（MCP server）、okfcli（CLI）、okf-skills（Claude Code plugin） |
| **Agent Skill** | 教 agent 如何產出/消費 OKF 的指令集 | `okf-skills` 的 `/okf:okf` skill、`awesome-okf` 的 Claude Code skills |
| **MCP Server** | 讓 agent 透過 MCP 協定存取 OKF bundle 的服務 | OKFy 的 `serve --mcp`、`search_concepts/read_concept/get_neighbors` 工具 |

**結論**：OKF 本身是規格/格式。若你想讓 AICodeAgent 直接使用，需透過生態工具（OKFy MCP server 或 okf-skills plugin）橋接。

### Q2：我公司現在如果有給每個專案都維護一份 DataModel/BusinessLogic，那這工具可以如何使用，以及用了會有何效果

**A**：可以將既有的 DataModel/BusinessLogic 文件轉換為 OKF bundle，讓 AI agent 可直接查詢與引用。

**使用路徑（4 步驟）**：

```
Step 1: 轉換既有文件為 OKF
  ┌─────────────────────────────────────────────┐
  │ 既有 DataModel (ERD, SQL DDL, dbt YAML)   │
  │ 既有 BusinessLogic (runbook, wiki, doc)    │
  └──────────────┬──────────────────────────────┘
                 ▼
  ┌─────────────────────────────────────────────┐
  │ OKF bundle (每個 table/logic 一個 .md)      │
  │ 例如:                                       │
  │   datamodel/                                │
  │   ├── tables/orders.md                      │
  │   ├── tables/customers.md                   │
  │   └── business-logic/                       │
  │       ├── revenue-calculation.md             │
  │       └── refund-policy.md                  │
  └──────────────┬──────────────────────────────┘

Step 2: 放入專案 git repo（與程式碼同倉庫或獨立 repo）
  └── 可 PR review、git diff、blame

Step 3: 啟動 MCP server 供 agent 查詢
  └── npx okfy-ai serve ./okf --mcp

Step 4: Agent 透過 MCP 查詢
  └── search_concepts("orders table") → read_concept("tables/orders")
```

**轉換方式**：

| 既有格式 | 轉換工具 | 說明 |
|----------|----------|------|
| dbt YAML + docs | `okfy-ai import ./target/compiled` | dbt 已產出 Markdown 文件，直接 import |
| SQL DDL 註解 | 自訂 script → OKF | 解析 `COMMENT ON TABLE/COLUMN` 產出 frontmatter |
| 既有 Wiki/Notion | `okfy-ai crawl <url>` | 爬取網站轉 OKF |
| 手寫 Markdown | 直接放入 bundle 目錄 | 加 frontmatter 即可 |
| ERD 圖 | 手動撰寫對應的 `.md` | OKF 不支援圖片，但可在 body 中用文字描述 schema |

**預期效果**：

| 面向 | 使用前 | 使用後 |
|------|--------|--------|
| **agent 查詢 DataModel** | 每次重新讀整份文件或靠 RAG | 精準搜尋 + 漸進式讀取，只讀需要的 table |
| **跨專案共享** | 各專案各自維護，格式不一 | 統一 OKF 格式，跨專案 agent 可直接引用 |
| **版本管理** | 文件散落各處，無版本追蹤 | git diff 可看到 schema 變更歷史 |
| **知識新鮮度** | 文件常過期 | CI 可驗證 bundle validity；社群工具 surface 可 code change → build fail |
| **新成員 onboarding** | 需人工閱讀多份文件 | Agent 可回答「orders table 的 schema 是什麼？」 |

**反證**：若團隊無 git 習慣、無 agent 使用場景、或 DataModel 極少變動，導入 OKF 的效益有限。OKF 不解決「沒有人寫文件」的問題。

### Q3：我個人使用時有沒有可能拿它來做「我個人第二大腦的存取介面」？如何配置？（以 opencode/claudecode 為例）

**A**：可以。OKF bundle 可作為個人第二大腦的儲存格式，搭配 MCP server 作為存取介面。

**目錄結構範例**：

```
~/second-brain/
├── index.md
├── log.md
├── projects/
│   ├── index.md
│   ├── project-alpha.md
│   └── project-beta.md
├── learnings/
│   ├── index.md
│   ├── rust-ownership.md
│   └── k8s-networking.md
├── people/
│   ├── index.md
│   └── alice.md
└── decisions/
    ├── index.md
    └── why-choose-okf.md
```

**opencode 配置**：

opencode 支援 MCP server（透過 `opencode.json` 設定）。在專案或全域 `opencode.json` 中加入：

```json
{
  "mcpServers": {
    "second-brain": {
      "command": "npx",
      "args": ["-y", "okfy-ai", "serve", "~/second-brain", "--mcp"],
      "enabled": true
    }
  }
}
```

配置後，opencode 中的 agent 可透過以下工具存取你的第二大腦：

- `search_concepts("rust ownership")` — 搜尋相關概念
- `read_concept("learnings/rust-ownership")` — 讀取完整內容
- `get_neighbors("learnings/rust-ownership")` — 遍歷關聯概念

**claudecode 配置**（三種方式）：

| 方式 | 指令 | 適用場景 |
|------|------|----------|
| **MCP（推薦）** | `claude mcp add --transport stdio second-brain -- npx -y okfy-ai serve ~/second-brain --mcp` | 最輕量，無需安裝 plugin |
| **Plugin** | `/plugin install okf@scaccogatto` | 需完整 OKF 工具鏈（produce/validate/visualize） |
| **Skill** | `npx skills add scaccogatto/okf-skills` | 需 skills.sh 生態整合 |

**CLAUDE.md 自動化提示**（貼入專案 `CLAUDE.md` 或 `~/.claude/CLAUDE.md`）：

```
Before answering questions about my personal knowledge, consult the
second-brain MCP server. Search for relevant concepts first, read
only the strongest matches, and cite the source file path.
```

**效果對照**：

| 面向 | 無 OKF | 有 OKF |
|------|--------|--------|
| 知識存放 | 散落各處（Obsidian/Notion/備忘錄） | 單一目錄結構，git 版本管理 |
| Agent 存取 | 需手動貼入 context 或靠 RAG | MCP 精準搜尋 + 漸進式讀取 |
| 跨 agent 共享 | 同一份知識需重複配置 | 同一 bundle 可同時供 opencode/claudecode 使用 |
| 知識更新 | 手動編輯後 agent 不知 | Agent 可讀最新版本（auto-refresh） |
