# search-from-mybrain 的 15 場景設計邏輯與實際命中案例

> 本報告解析 `search-from-mybrain` skill 中「五層級 × 三問 = 15 場景」的設計邏輯，並從第二大腦 FATESAIKOU/MyBrain 的骨幹檔與日誌中舉出 3 個實際命中案例。

---

## 1. 這個技術解決什麼問題？

**LLM agent 無法判斷「什麼時候該查使用者個人上下文」的觸發閘門問題。**

具體來說，`search-from-mybrain` 在定義層面解決了三個子問題：

1. **觸發條件模糊**：agent 知道「應該查使用者背景」，但不知道「什麼問題才算需要查」。哲學三問（我是誰／我在哪裡／我要去哪）太抽象，無法直接對應到具體對話場景。
2. **查詢範圍不明確**：即使決定要查，agent 也不知道「該去第二大腦的哪個目錄找答案」。15 場景的「找哪裡」欄位將抽象問題映射到具體目錄路徑。
3. **遺漏風險高**：agent 容易在「自認知道答案」的場景跳過查詢，給出與使用者既有立場衝突的建議。15 場景的設計目標是**降低遺漏率**，讓 agent 在不確定時優先查。

---

## 2. 這個問題為什麼會發生？（背景）

### 2.1 抽象三問無法直接操作

哲學三問（我是誰／我在哪裡／我要去哪）是 skill 的設計原點，但直接拿來當觸發條件會遇到兩個問題：

| 問題 | 表現 |
|---|---|
| **覆蓋範圍模糊** | 「我是誰」可以涵蓋身份、價值觀、技術偏好、金融原則——但 agent 無法從一句「推薦一個框架」判斷這屬於哪一層的「我是誰」 |
| **查詢路徑不明** | 知道要查「我是誰」之後，該去 `日常/生活` 還是 `抽象理解/價值觀`？兩者都回答「我是誰」，但面向不同 |

### 2.2 通用 agent 的預設偏誤

LLM 訓練資料讓 agent 傾向於給出「一般情況下的最佳答案」。當使用者已經有明確立場時，通用答案會與使用者既有決策衝突。例如：

- agent 推薦某個框架，但使用者已在第二大腦中標記為「不採用」
- agent 建議某種職涯路徑，但使用者有「不能喪失技術手感」的硬約束

### 2.3 現有觸發機制的不足

| 方案 | 限制 |
|---|---|
| 每次都查 | token 浪費，90% 的查詢不需要個人上下文 |
| 靠 agent 自行判斷 | 依賴 LLM 的內隱知識，不穩定且不可驗證 |
| 寫死在 AGENTS.md | 靜態規則無法涵蓋動態變化的對話場景 |

### 2.4 通用技術背景

- **Contextual trigger design** 是 AI agent 系統中的經典問題：何時該檢索外部知識、何時該依賴模型內參知識
- 類似概念見於 RAG 系統的「檢索決策」（retrieval decision）、agent 框架的「tool calling trigger」
- `search-from-mybrain` 的 15 場景是**規則式觸發**（rule-based trigger），而非模型自行判斷

## 3. 這個技術是如何解決該問題的？

### 3.1 設計邏輯：五層級 × 三問 = 15 格

核心做法是將抽象的哲學三問，與五個具體的生活層級做笛卡兒積，產生 15 個可操作的觸發場景：

```
三問（抽象）                   五層級（具體）
─────────────────     ─────────────────────
我是誰                   日常生活
我在哪裡         ×       技術決策
我要去哪                 職涯取捨
                         金融戰略
                         人生議題
```

每一格定義三個要素：

| 要素 | 說明 | 範例（技術 × 我在哪裡） |
|---|---|---|
| **什麼時候算命中** | 具體的觸發條件 | 提到任何具體的工具、框架、模型名稱時 |
| **找哪裡** | 對應的第二大腦目錄 | `技術/技術評估` |
| **為什麼要查** | 不查的風險 | 使用者可能已評估過且結論是「不採用」 |

### 3.2 15 場景的完整映射表

#### 一、日常生活 → `日常/生活`

| 三問 | 命中條件 | 找哪裡 | 不查的風險 |
|---|---|---|---|
| 我是誰 | 建議的答案會因身份、家庭、稅務、收入結構而不同 | 骨幹、`日常/生活` | 套用「一般日本上班族」預設，與實際條件不符 |
| 我在哪裡 | 問到某個制度、申請、手續的進度或資格 | `日常/生活`、`日誌/` | 建議他早就做過或已卡住的做法 |
| 我要去哪 | 生活類的「下一步該做什麼」 | `日常/生活` | 建議他早就試過且放棄的行動 |

#### 二、技術決策 → `技術/`

| 三問 | 命中條件 | 找哪裡 | 不查的風險 |
|---|---|---|---|
| 我是誰 | 要推薦技術方案時 | 骨幹、`抽象理解/本質洞察` | 推薦到他反對的方向（如「用現成的比較快」vs 他的理解優先原則） |
| 我在哪裡 | 提到任何具體的工具、框架、模型名稱時 | `技術/技術評估` | 推薦他已評估過且「不採用」的方案 |
| 我要去哪 | 要動既有的專案，或討論下一步做什麼 | 骨幹、`技術/動手做`、`技術/追加功能`、`技術/靈感` | 建議與進行中實作脫節的下一步 |

#### 三、職涯取捨 → `日常/職涯`

| 三問 | 命中條件 | 找哪裡 | 不查的風險 |
|---|---|---|---|
| 我是誰 | 談到角色定位、該不該接某類工作 | 骨幹、`日常/職涯` | 建議違反「不能喪失技術手感」硬約束的角色 |
| 我在哪裡 | 涉及現職內容與環境，或對就業市場的判斷 | `日常/職涯` | 基於過時或錯誤的現職理解給建議 |
| 我要去哪 | 轉職、升遷、技能投資 | 骨幹、`日常/職涯`、`抽象理解/人生方向` | 用市場行情取代他個人的判準 |

#### 四、金融戰略 → `日常/金融`

| 三問 | 命中條件 | 找哪裡 | 不查的風險 |
|---|---|---|---|
| 我是誰 | 談投資時 | 骨幹、`日常/金融` | 給出與既定紀律衝突的建議（如「現在該加碼」vs 他的「定期定額不因行情調整」） |
| 我在哪裡 | 問現在該怎麼配置、加碼或減碼 | `日常/金融` | 忽略他已有的判定結果，從零重推 |
| 我要去哪 | 中長期配置、換匯、定投年限 | 骨幹、`日常/金融` | 建議他已經跑過分析的方案 |

#### 五、人生議題 → `抽象理解/`

| 三問 | 命中條件 | 找哪裡 | 不查的風險 |
|---|---|---|---|
| 我是誰 | 任何涉及價值判斷的問題 | 骨幹、`抽象理解/價值觀`、`抽象理解/本質洞察` | 用通則回答他已有明確立場的問題 |
| 我在哪裡 | 盤點現況、檢視「過得怎麼樣」 | 骨幹、`抽象理解/人生方向`、`日誌/` | 製造不存在的問題或忽略前瞻性風險 |
| 我要去哪 | 長期目標、人生規劃、優先順序 | 骨幹、`抽象理解/人生方向`、`抽象理解/想法` | 用別的框架硬套他已有的目標設定方法論 |

### 3.3 設計上的三個關鍵決策

**決策一：規則式觸發而非模型判斷**

15 場景全部用「命中條件」的 if-then 規則定義，不依賴 LLM 自行判斷「這需不需要查個人上下文」。理由是：

- 規則可驗證、可除錯
- 規則可迭代（新增場景不影響既有邏輯）
- 規則的遺漏是可追蹤的（某個場景沒被觸發 = 規則沒寫到）

**決策二：三問 × 五層級 = 15 格，而非更少或更多**

- 少於 15 格（如只分層級不問三問）：同一層級內的三問指向不同目錄，合併會遺失精度
- 多於 15 格（如再細分 sub-level）：增加維護成本，且 15 格已涵蓋所有已知命中場景

**決策三：每格都指定「找哪裡」，而非開放式搜尋**

- 指定目錄路徑讓 agent 的搜尋範圍從「整個第二大腦」縮小到「特定子目錄」
- 減少無關結果的雜訊
- 加速檢索（熱鏡像下約 1 秒）

### 3.4 虛擬碼

```
def should_search_mybrain(user_message, conversation_context):
    # 15 場景的觸發規則
    triggers = [
        # 技術 × 我在哪裡
        {"condition": contains_tool_name(user_message),
         "search_path": "技術/技術評估",
         "reason": "使用者可能已評估過該工具"},
        
        # 技術 × 我要去哪
        {"condition": mentions_existing_project(user_message),
         "search_path": "技術/動手做",
         "reason": "下一步需接軌進行中實作"},
        
        # 人生 × 我是誰
        {"condition": involves_value_judgment(user_message),
         "search_path": "抽象理解/價值觀",
         "reason": "使用者有明確的價值判斷立場"},
        
        # ... 其餘 12 格
    ]
    
    for trigger in triggers:
        if trigger["condition"]:
            return True, trigger["search_path"], trigger["reason"]
    
    return False, None, None
```

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式？

### DA 表

| 技術名 | 技術解法 | 技術使用前提 | 技術使用副作用 | 技術使用預期效果 |
|---|---|---|---|---|
| **LLM 自行判斷** | 不預定義觸發規則，讓 LLM 自行決定何時需要查使用者上下文 | LLM 需有足夠的 instruction following 能力 | 判斷不穩定；無法驗證；遺漏無法追蹤 | 實作最簡單，但可靠性最低 |
| **單一觸發條件** | 只設一條規則（如「提到工具名就查」），不區分層級與三問 | 使用者上下文資料量小，查詢成本低 | 過度觸發（無關問題也查）；查詢範圍太廣，結果雜訊多 | 實作簡單，但精確度低 |
| **向量相似度觸發** | 將使用者問題向量化，與預定義的「需查詢場景」做相似度比對 | 需建置 embedding pipeline；需標註訓練資料 | 語意邊界模糊；冷啟動需人工標註 | 檢索彈性高，但觸發邊界不清晰 |
| **分層決策樹** | 先判斷層級（技術/職涯/金融/人生），再判斷三問，最後決定查哪裡 | 需明確定義每層的判斷條件 | 決策路徑固定，無法處理跨層級問題 | 結構清晰，但靈活性低 |

### 切入點差異

- **LLM 自行判斷** vs 15 場景：前者將觸發決策委託給模型，後者用規則鎖死。15 場景的優勢在於可驗證性——你可以測試「提到工具名時是否觸發」，但無法測試「LLM 是否自行判斷正確」。
- **單一觸發條件** vs 15 場景：前者是 flat 結構，後者是 5×3 矩陣。15 場景的矩陣結構讓「找哪裡」更精確——同樣是「技術」層級，「我是誰」去骨幹、「我在哪裡」去技術評估、「我要去哪」去動手做，三個目錄完全不同。
- **向量相似度觸發** vs 15 場景：前者是語意驅動，後者是規則驅動。15 場景不怕語意邊界模糊的問題——「提到工具名」是確定性條件，不需要 embedding 判斷。
- **分層決策樹** vs 15 場景：兩者都是結構化觸發，但 15 場景的笛卡兒積設計確保了所有組合都被覆蓋，而決策樹可能因分支剪枝而遺漏某些組合。

## 5. 實際命中案例（從第二大腦骨幹檔與日誌提取）

以下三個案例來自 FATESAIKOU/MyBrain 的骨幹檔與日誌，展示 15 場景中最常被觸發的三格。

### 案例一：技術 × 我在哪裡（最頻繁觸發）

**觸發條件**：提到任何具體的工具、框架、模型名稱時。

**第二大腦中的對應資料**：

`技術/技術評估/判定總表.md` 記錄了 79 篇技術評估的判定結果：

| 判定 | 數量 | 代表案例 |
|---|---|---|
| 採用 | 18 | OmniRoute、Hallmark、Aionui、Strix、Maigret、agent-skills、LeanCtx、Headroom |
| 試用 | 10 | — |
| 觀望 | 5 | — |
| 不採用 | 40 | Browser-use、terminal-browser、DeerFlow、ego-lite 等 |
| 未判定 | 6 | — |

**典型查詢模式**：

```
使用者：推薦一個 browser automation 工具
agent 查第二大腦 → 發現 Browser-use 已被標記為「不採用」
agent 不推薦 Browser-use，改推薦其他方案或詢問使用者的具體需求
```

**不查的風險**：agent 可能推薦 Browser-use（因為它在 GitHub 上很熱門），但使用者已判定「效率不優，乾脆自己兜好」。

**日誌佐證**：`日誌/2026-07-26.md` 記錄了 Browser-use 的判定日期。

---

### 案例二：技術 × 我要去哪

**觸發條件**：要動既有的專案，或討論下一步做什麼。

**第二大腦中的對應資料**：

`技術/動手做/專案現況表.md` 記錄了 20 個動手做專案的現況：

| 狀態 | 數量 | 代表案例 |
|---|---|---|
| 日常在用 | 4 | Learning、LearnGhAgent、投資決策 Dashboard、自動閱讀 Feedly |
| 進行中 | 1 | 完善化 BrowserBase |
| 理解已達成 | 10 | Pixel FeliCa、OfficeCLI、OpenDesign、GAS 自動閱讀信件等 |
| 索引檔 | 5 | — |

**典型查詢模式**：

```
使用者：要不要把那個 Feedly 自動閱讀再強化一下？
agent 查第二大腦 → 發現「自動閱讀 Feedly」已是「日常在用」狀態
agent 不建議「強化」，而是問「目前卡在哪裡」或「想新增什麼功能」
```

**不查的風險**：agent 可能建議「先做 MVP」，但該專案早已越過 MVP 階段進入日常使用。

**⚠️ 關鍵標記**：`專案現況表.md` 明確標註「不要把『理解已達成』當成失敗或技術債」。如果 agent 不查這格，可能會建議使用者「把那些坑填完」，但使用者多數 MVP 的正常結局就是「理解已達成，不需要繼續」。

---

### 案例三：人生 × 我是誰

**觸發條件**：任何涉及價值判斷的問題。

**第二大腦中的對應資料**：

`抽象理解/價值觀/核心價值觀.md` 定義了兩條北極星：

1. **做出真的有人在用的東西，且有高度不可替代的價值**
2. **健康穩定地活著**

`抽象理解/價值觀/不做清單.md` 定義了兩層硬度的負面約束：

| 層級 | 內容 | 觸發行為 |
|---|---|---|
| 即時線 | 被要求做不誠實或違法的事 | 當場走，不進入權衡 |
| 驗證後退出 | 其餘全部（含「產出只到判斷材料為止」等 7 條） | 全力嘗試改變 → 驗證 → 才決定退出 |

**典型查詢模式**：

```
使用者：你覺得去當純技術顧問怎麼樣？
agent 查第二大腦 → 發現「產出只到判斷材料為止」在不做清單中
agent 不推薦純顧問角色，因為違反「不能喪失技術手感」的硬約束
```

**不查的風險**：agent 可能推薦「技術顧問」作為職涯選項，但使用者從顧問業離職的直接原因就是「產出只到判斷材料為止、不負責讓它動起來」。

**⚠️ 關鍵標記**：`不做清單.md` 標註「不要建議他『快速止損、趕快離開』」，因為使用者的行為模式是「先試著改變，驗證後才退出」。如果 agent 不查這格，可能給出與使用者已驗證行為模式直接衝突的建議。

### 三個案例的對照總結

| 面向 | 案例一：技術 × 我在哪裡 | 案例二：技術 × 我要去哪 | 案例三：人生 × 我是誰 |
|---|---|---|---|
| 觸發頻率 | 最高（每次提到工具名） | 中（討論專案下一步時） | 中高（涉及價值判斷時） |
| 第二大腦資料量 | 79 篇技術評估 | 20 個專案狀態 | 3 份骨幹檔（核心價值觀、不做清單、技術取捨準則） |
| 不查的典型錯誤 | 推薦已 reject 的工具 | 建議已完成的 MVP | 推薦違反價值觀的角色 |
| 查詢成本 | 低（grep 工具名即可） | 低（查專案現況表） | 低（讀骨幹檔 frontmatter） |
| 錯誤成本 | 中（浪費時間重新評估） | 低（浪費對話輪次） | 高（給出與使用者立場衝突的建議） |
