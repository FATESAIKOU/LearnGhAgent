# 212_R2_step3-qa.md

## 狀況理解

R2 為 QA loop：使用者對 R1 報告提出三個質問型問題——(Q1) 這是不是 PDF 解析框架、(Q2) 通用需求應選最穩定套件、速度次選、(Q3) 這種「有明確答案、非架構或需求層級」的抽象需求學習優先度是否很低。核心是重新評估 pdf-inspector 的定位與學習優先度，而非索取新技術細節。本 step 將這三問構造化沉澱進報告 §5，並以第二大腦的既有判定（MarkItDown Accept、技術取捨準則）與 Step 2 取得的成熟度證據回應。R1 報告無 §5，故本輪為首次新增。

## 動作結束後的現狀

**產出的報告：** `output/212_pdf-inspector.md`（檔名沿用 R1，§1–§4 內容不刪改）。

**本輪變更摘要：** 於 §4 與附錄之間**首次新增 `## 5. User Q&A`**，含 Q1–Q3：

| QA | 核心回應 |
|---|---|
| Q1 是不是解析框架 | 否。底層解析交給唯一依賴 `lopdf`；pdf-inspector 是建於其上的分類＋抽取＋轉換應用工具 |
| Q2 穩定優先、速度次選 | 準則成立但導向「不選它」——無 Release、Cargo/tag/PyPI 版本不一致、半年專案、commit 有空窗；MarkItDown 已 Accept 定稿，依汰換準則不因「更好」而換 |
| Q3 這種抽象需求優先度 | 拆成「工具層（不學）＋機制/思路層（抽 smart routing）」；優先度低但前提「有明確答案」部分不成立 |

**第二大腦判定標注：** MarkItDown Accept（本人 `stable`，URL 已標）；技術取捨準則為 `claude-code/opus-5` `draft`（⚠️ 未經本人 review，已註明）；判定總表為 `deepseek-v4-flash` `draft`。pdf-inspector 在第二大腦無判定（明寫無）。

**硬性驗證：** 報告總長度 47,7xx 字 < 上限 50000；§1–§4 既有內容未刪改；Q&A 依序遞增且每個子問題獨立一則；檔案落在 `output/`。log 長度 < 3000 字。
