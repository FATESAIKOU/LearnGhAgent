# Step 1 - 意圖理解 Review 觀點

> 軟性驗證 Step 1 產出時，LLM 應採用的 review 觀點。

## 驗證項目

| 項目 | 結果 | 備註 |
|------|------|------|

1. **檢查範圍明確性**：是否從 PR body 正確辨識出要檢查的程式碼範圍（目錄、檔案、專案）？
2. **工具需求識別**：是否正確判斷需要執行哪些檢查（ESLint / Prettier / TS / 覆蓋率）？
3. **條件列舉**：關鍵條件是否被窮舉（忽略規則、特定目錄、閾值要求等）？
4. **缺乏資訊識別**：是否有指出需要補查的資訊缺口（如專案結構未知）？
5. **log 格式合規**：4 個 section 是否齊全且順序正確？長度是否在限制內？
6. **第二大腦查詢**：是否確實查過 MyBrain 確認要審的是他哪個專案、進行到哪一步？「## 執行的動作與結果」裡要有查詢紀錄，每則發現帶 GitHub URL 與信任層級（`generated.by` / `status`）。**查不到而明寫「第二大腦無此主題」也算通過**——沒查、或查不到卻用通用知識填空還講得像是他的舊結論，一律 FAIL。
