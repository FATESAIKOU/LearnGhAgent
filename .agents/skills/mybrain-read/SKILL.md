# mybrain-read

```
REPO   = https://github.com/FATESAIKOU/MyBrain   （private）
鏡像   = /tmp/mybrain                            （唯讀，可覆寫 $MYBRAIN_DIR）
```

## 這裡面裝的是什麼

**這個第二大腦是使用者對哲學三問的線索庫**——涵蓋過去、現在與未來，不限任何主題範圍：

1. **我是誰**：他的判斷準則、價值觀、自我定位
2. **我在哪裡**：他現在的處境、身份、部位、已經下過的判斷
3. **我要去哪**：他打算做什麼、還沒做完什麼、卡在哪裡

但這三問太抽象，沒辦法直接拿來判斷「現在該不該查」。下面把它翻譯成**五個層級 × 三問 = 15 個具體場景**，外加一個跨領域的第〇格。

## 目錄結構

三條主題軸各分二層，加兩條扁平的軸。**這是規則一定義的結構，穩定；裡面有哪些檔案則會持續增加。**

```
技術/      {靈感, 技術評估, 動手做, 追加功能}      工具、技術、實作
抽象理解/  {想法, 本質洞察, 價值觀, 人生方向}      抽離情境仍成立的理解
日常/      {日常溝通, 金融, 生活, 職涯}            生活、金錢、人際
日誌/      （扁平，YYYY-MM-DD.md）                 時間軸
專案/      （扁平）                                還沒做完的事——目前只有下一步清單
```

子分類可能增補，所以**實際有哪些目錄與檔案，一律以步驟 2 讀到的內容為準**，不要憑本檔推測。

## 兩個檔內標記

bundle 用兩個記號標出「機器該特別對待」的段落。**它們是約定，不是內容**——本檔不複製任何一則的實際文字，去讀檔案。

| 記號 | 意思 | 你該怎麼做 |
|---|---|---|
| `⚠️ **不要…**` | 他明確講過、而**直覺會反過來猜**的事 | **讀到就必須遵守。** 這是「查到之後才會犯的錯」，比查不到更危險——因為你會很有自信地講錯 |
| `🔄` | 該段落是**事後由 AI 校正加上去的**，本人尚未 review | 照 `draft` 處理，即使該檔的 frontmatter 是 `stable` |

## 骨幹：先讀，不要一上來就 grep

**bundle 有一組檔案的 frontmatter 帶 `骨幹` tag。** 它們是為了直接回答上面三問而寫的，多數問題讀一到兩份就夠。

```bash
grep -rl '^tags: \["骨幹"' "$MB" --include='*.md' --exclude-dir=.okf --exclude=index.md --exclude=log.md
```

哪些檔帶這個 tag、各自寫了什麼，**以跑出來的結果為準**——bundle 會長，本檔不列清單。從檔名與 frontmatter 的 `description` 判斷該讀哪一份。

⚠️ **骨幹檔是策展過的結論，不是全部。** 具體的工具名、數字、某次判定的理由仍然只在個別檔案的內文裡，那要靠 grep。

## 必須先查第二大腦的場景（第〇格 + 15 格）

下表的「找哪裡」是**依目錄的定義**指路，不是宣告那裡現在有什麼。**某一格查不到就是查不到**（照步驟 5 的規則明說），不要因為本檔提過就腦補內容。

**這些場景是「先查再答」，不是「查了更好」。** 命中任何一格就先跑完步驟 1–4 再開口。

### 〇、跨領域：他現在在做什麼 → `專案/下一步清單.md`

這一格不分領域，命中就直接讀那一份檔：

| 什麼時候算命中 | 為什麼 |
|---|---|
| 他問「我現在在做什麼」「接下來該做什麼」「我手上有什麼」 | 直球問題，答案整份都在那裡 |
| 他要**新開一件事**，或問你某件事值不值得做 | 他可支配時間只有 10～20 小時／週，**不足以同時推進多線**。不看清單就會建議他再開一條，而那必然要取代掉什麼 |
| 他說某件事「卡住了」「還沒動」 | 先確認那件事在不在清單上、清單裡寫的下一步是什麼——他可能早就想過下一步，只是沒做 |

那份檔是**覆寫式快照，整份就是現在**，不需要判斷哪一段才是最新的。每條帶「來源」連回原本的行動計劃，要細節就跟著連結走；另有「所屬領域」與「期限」兩欄——期限的 `—` 意思是「查過了，沒有硬期限」，不是漏填。

⚠️ **卡點不在清單裡。** 問「為什麼推不動」要去 `抽象理解/人生方向/現況盤點.md`，清單只寫該動作為何被挑出。

⚠️ **清單裡沒有的事不代表他沒在做。** 它只收「可直接執行的單一動作」——沒有明確下一步的長期議題（例如他最卡的「架構師之後的定位」）留在現況盤點，不在清單上。

### 一、日常生活 → `日常/生活`

| 三問 | 什麼時候算命中 | 找哪裡 |
|---|---|---|
| 我是誰 | 你要建議的事，答案會**因他的身份、家庭、稅務、收入結構而不同**。先查他的實際條件，不要套「一般日本上班族」的預設 | 骨幹、`日常/生活` |
| 我在哪裡 | 問到某個制度、申請、手續**目前進行到哪一步**、他有沒有某項資格 | `日常/生活`、`日誌/` |
| 我要去哪 | 生活類的「下一步該做什麼」。這類事情他常寫成**行動計劃**，計劃裡會記卡點與待辦——不查就可能建議他早就試過的做法 | `日常/生活`、第〇格的清單 |

### 二、工作上的技術決策 → `技術/`

| 三問 | 什麼時候算命中 | 找哪裡 |
|---|---|---|
| 我是誰 | 要推薦技術方案時。他對「什麼時候該自己兜、什麼時候用現成的」「AI agent 的信任邊界」這類問題有沉澱下來的準則，**照通則推薦可能推到他反對的方向** | 骨幹、`抽象理解/本質洞察` |
| 我在哪裡 | **提到任何具體的工具、框架、模型名稱時**——先確認他是不是已經評估過、結論是什麼。**查到「Reject」時先讀骨幹裡關於判定語意的說明再轉述**，那個詞的意思跟你以為的可能不同 | `技術/技術評估` |
| 我要去哪 | 要動他既有的專案，或討論下一步做什麼。改動要接得上進行中的實作與已排的追加功能 | 骨幹、`技術/動手做`、`技術/追加功能`、`技術/靈感`、第〇格的清單 |

### 三、職涯上的取捨 → `日常/職涯`

| 三問 | 什麼時候算命中 | 找哪裡 |
|---|---|---|
| 我是誰 | 談到他的角色定位、該不該接某類工作、怎麼描述自己的專業 | 骨幹、`日常/職涯` |
| 我在哪裡 | 涉及**現職的內容與環境**，或他對當前就業市場的判斷 | `日常/職涯` |
| 我要去哪 | 轉職、升遷、要不要投資某項技能。**先找他自己的判準，那比市場行情更決定答案** | 骨幹、`日常/職涯`、`抽象理解/人生方向` |

### 四、金融議題上的戰略 → `日常/金融`

| 三問 | 什麼時候算命中 | 找哪裡 |
|---|---|---|
| 我是誰 | 談投資時。**先確認他有沒有既定的紀律或原則**——若有而你給了相衝突的建議，等於叫他破戒 | 骨幹、`日常/金融` |
| 我在哪裡 | 問現在該怎麼配置、加碼或減碼。他會定期產出判定與調整紀錄，**先看他自己的判定結果再說** | `日常/金融` |
| 我要去哪 | 中長期配置、換匯、定投年限這類跨年度的規劃。他可能已經跑過分析，別從零重推 | 骨幹、`日常/金融` |

⚠️ 判定報告裡的數字**未必是紀律**——同一個 bundle 裡「當期決策」與「不變原則」是分開的兩種東西，骨幹檔會講清楚哪個是哪個。轉述前先確認。

### 五、人生議題上的選擇 → `抽象理解/`

| 三問 | 什麼時候算命中 | 找哪裡 |
|---|---|---|
| 我是誰 | 任何涉及**價值判斷**的問題——什麼對他重要、什麼是他不做的。**這是最不該用通則回答的一格** | 骨幹、`抽象理解/價值觀`、`抽象理解/本質洞察` |
| 我在哪裡 | 他在盤點現況、檢視「我現在過得怎麼樣」，或問題橫跨生活與工作 | 骨幹、`抽象理解/人生方向`、第〇格的清單、`日誌/` |
| 我要去哪 | 長期目標、人生規劃、優先順序。**他可能有自己的目標設定方法論**，用別的框架硬套會格格不入 | 骨幹、`抽象理解/人生方向`、`抽象理解/想法` |

---

**這 15 格（加上第〇格）的共同點**：答案取決於你不知道的個人脈絡。**用通用知識回答一個他已經有立場的問題，比不回答更糟**——他會拿到一個和自己過去的決定相衝突、卻沒說明為什麼的答案。

不確定有沒有命中就**查**。熱鏡像查一次約 1 秒，代價遠低於給錯建議。

## ⚠️ 唯讀

`/tmp/mybrain` 是鏡像，**一個字都不准改**，改了下次 refresh 就被 `reset --hard` 沖掉。要寫東西進第二大腦一律走 `/mybrain-write`。

## 步驟 1：更新鏡像

```bash
bash "$(dirname "$0")/refresh.sh"      # 或 skill 目錄下的 refresh.sh 絕對路徑
MB="${MYBRAIN_DIR:-/tmp/mybrain}"
```

冪等。session 啟動時通常已經跑過一次（熱的時候約 1 秒，冷啟動要 clone 約 30 秒），但**每次搜尋前還是要跑**——你不能假設 hook 有跑、也不能假設這個 session 開了多久。

失敗了它會印警告並沿用舊副本，這時**要在回報裡註明資料可能過期**，不要當作沒事。

---

## 步驟 2：先讀骨幹，判不出來才掃目錄

```bash
grep -rl '^tags: \["骨幹"' "$MB" --include='*.md' --exclude-dir=.okf --exclude=index.md --exclude=log.md
```

挑一到兩份用 Read 讀**全文**。它們本身就是策展過的結論。

骨幹涵蓋不到、或判不出該讀哪份時，再掃各層目錄。各檔 frontmatter 的 `description` 是一句話摘要，**一個檔一行**，整份一次讀完就有全局視野（幾百行等級，不是幾千行）：

```bash
find "$MB" -name index.md -not -path '*/.*' ! -path "$MB/index.md" -exec cat {} +
```

排除根 `index.md`——那裡面是 bundle 的「使用規則」，寫入時才需要，搜尋用不到。

---

## 步驟 3：grep 補骨幹與目錄沒涵蓋的詞

`description` 只有一句話，具體的工具名、錯誤訊息、數字通常只在內文：

```bash
grep -rn "關鍵詞" "$MB" --include='*.md' --exclude-dir=.okf --exclude-dir=.github
```

- 中文與英文都試。技術詞彙他常中英混用（「模型」／`model`）
- 檔名本身也是線索，而且是中文的：`ls -R "$MB"` 掃一遍不貴
- 一個詞查不到就換同義詞再試，**不要查一次沒中就宣告沒有**

---

## 步驟 4：讀命中的檔案

用 Read 工具讀全文，不要只看 grep 的那一行——結論的**理由**往往在前後段，而理由才是有價值的部分。

**掃一遍檔內有沒有 `⚠️` 與 `🔄`**（見上方「兩個檔內標記」）。`⚠️` 的段落即使跟你要回答的問題只沾到邊，也要遵守。

同時查它的時間座標：

```bash
grep -rl "檔名.md" "$MB/日誌/"
```

規則是**第一次被日誌連結＝這則知識誕生的時間，之後每次＝一次更新**。所以這串日期就是「他什麼時候想的、又回頭改過幾次」。

---

## 步驟 5：回報

每則發現**一定要帶三個東西**，缺一不可：

| 要素 | 怎麼取得 |
|---|---|
| **GitHub URL** | `https://github.com/FATESAIKOU/MyBrain/blob/main/<路徑>`，空格編碼成 `%20`（中文不用編碼） |
| **信任層級** | 看 frontmatter 的 `generated.by` 與 `status`，再看段落有沒有 `🔄`（見下） |
| **時間座標** | 步驟 4 查到的日誌日期 |

### 信任層級（最重要的一件事）

**兩個欄位一起看，順序是先 `generated.by`（誰寫的）再 `status`（定稿了沒）**：

| `generated.by` | `status` | 怎麼講 |
|---|---|---|
| `human:fatesaikou` | `stable` | 他本人寫的，可以直接當成他的結論 |
| 任何 AI（`opencode/…`、`claude-code/…`） | `draft` | **一定要標「這是當時的 AI 草稿，你還沒 review」** |
| `process:…`（自動流程產出） | `stable` | 機器產的，講的時候點名來源，別說成他的判斷 |
| 任何 | `draft` | 未定稿，語氣要留餘地 |

⚠️ **檔案層級的信任不代表段落層級的信任。** `stable` 的檔案裡可能有 `🔄` 段落（事後 AI 校正、未經 review），`draft` 的檔案裡可能有直接引用他原話的段落。**看到「原話：」引號內的是他說的；看到「推測：」開頭的是 AI 推論，轉述時務必分開。**

`verified` 欄位（含 `human:` actor）是更強的訊號，有就用。但⚠️ **不要把「沒有 `verified`」當成「不可信」**——這個欄位填得很稀疏，連使用者自己一個字一個字寫的檔案也常常沒填。若拿它當主判準，整個第二大腦都會被標成不可信，等於沒有標。**主要的區分力在 `generated.by`。**

把 AI draft 當事實轉述出去，是這個 skill 最大的風險——他會以為那是自己拍板過的決定。（完整的信任層級推導在 `okf-format` skill。）

### 找不到的時候

**直接說「第二大腦裡沒有這個主題」，然後才用一般知識回答，並且說清楚哪一段是哪來的。**

絕對不可以查不到就用通用知識填空、還講得像是他的舊結論。

**檔案裡的空欄位同理。** 有些檔是刻意先建骨架、內容慢慢補的——空著代表「還沒填」，不是「沒有」，更不是可以推測的空白。

### 寫法

- 講**結論與理由**，不要複述整篇。他要的是「我當時決定什麼、為什麼」
- 查到**行動計劃**時，重點是**目前卡在哪、下一步是什麼**，不是計劃全文
- 找到多份就按相關性排，不要全部倒出來
- 內容和你現在要說的話衝突時**明確指出衝突**，這正是查詢最有價值的時候

## 失敗處理

| 狀況 | 做法 |
|---|---|
| `gh` 未登入 | 提示 `gh auth login`。這是 private repo，不要改用裸 `git clone` |
| clone 失敗 | 回報並停止。不要去找本機有沒有其他 MyBrain 副本 |
| 更新失敗但有舊副本 | 照常查，但**在回報裡註明資料可能過期** |
| `骨幹` grep 結果為空 | 該 tag 可能還沒導入或改名。退回步驟 2 的掃目錄做法，不要停 |
| 查不到 | 明說沒有（見上），不要編 |
| 需要寫入 | 停下來，告訴使用者用 `/mybrain-write`。本 skill 唯讀 |
